## 1. Cloud vs On-Premises Deployment

Deploying an application in the cloud versus on-premises differs significantly across security, deployment speed, and resource management.

### Security

On-premises deployment gives the organisation full control over its physical infrastructure, firewalls, and data — useful when strict data sovereignty is required (e.g. a bank keeping customer records in its own data centre). However, the organisation bears full responsibility for patching, monitoring, and compliance. Cloud providers like Azure or AWS operate under a **shared responsibility model** — the provider secures the underlying infrastructure while the customer secures their applications and data. Cloud platforms also offer built-in tools like Azure Security Centre, DDoS protection, and identity management (e.g. Azure AD) that would be costly to replicate on-prem.

### Deployment Speed

On-premises deployments require procurement, racking, OS installation, and network configuration — often taking weeks or months. Cloud deployment can happen in minutes; for example, spinning up an Azure App Service or an AWS EC2 instance is essentially instant. CI/CD pipelines integrated with cloud platforms (e.g. GitHub Actions deploying to Azure) allow rapid, repeatable deployments that would require significant tooling investment on-prem.

### Resource Management

On-premises resources are fixed — if EventEase experiences a spike in traffic during a large event's ticket sale, the on-prem server may crash. Cloud platforms offer **auto-scaling**, meaning resources expand and contract with demand (e.g. Azure App Service scale-out rules). This also means cost is usage-based rather than capital-intensive, shifting from **CapEx to OpEx**.



## 2. IaaS vs PaaS vs SaaS and EventEase

**IaaS (Infrastructure as a Service)** provides raw compute, storage, and networking — the customer manages the OS, runtime, and application. Example: Azure Virtual Machines, AWS EC2. This offers maximum control but requires significant sysadmin effort.

**PaaS (Platform as a Service)** provides a managed platform including the OS, runtime, and middleware — the customer only manages the application code and data. Example: Azure App Service, Heroku, Google App Engine.

**SaaS (Software as a Service)** provides a fully managed application accessed by end users — no infrastructure or code management required. Example: Microsoft 365, Salesforce, Google Workspace.

| Aspect | IaaS | PaaS | SaaS |
| --- | --- | --- | --- |
| Customer manages | OS, runtime, app, data | App + data only | Nothing (just uses it) |
| Provider manages | Hardware, networking | Hardware through runtime | Everything |
| Flexibility | Highest | Moderate | Lowest |
| Maintenance burden | Highest | Low | None |

### Why PaaS Suits EventEase

EventEase is a custom ASP.NET Core MVC application — it can't simply be replaced by a SaaS product, so SaaS is out. IaaS would work but would require the team to manage VMs, patch operating systems, configure web servers, and handle scaling manually — overhead that's unnecessary for a web application. PaaS (e.g. Azure App Service) is ideal because:

- The team can deploy the MVC app directly without managing the underlying OS or IIS/Kestrel configuration.
- Built-in features like auto-scaling, SSL certificates, deployment slots, and monitoring (Application Insights) come out of the box.
- It integrates natively with the .NET ecosystem, supporting Entity Framework migrations, connection strings via App Settings, and CI/CD from GitHub.
- The team can focus on building EventEase features rather than infrastructure management, which aligns with a small development team's capacity.
